Vault secrets journey

Same request, five ways to get a database password

An orders API reads from Postgres. We run it side by side with the password hardcoded, with the password in Vault KV v2, and with dynamic credentials that Vault creates per request; with the optional Kubernetes profile also as a pod that logs in with its service account, and as a pod the Vault Secrets Operator looks after. Every button below sends a real request to the local stack. The diagrams animate the calls as they happen, and the activity panel in the corner lists them.

  1. Stage 1No Vault

    The password is in the app's environment, shared and permanent.

  2. Stage 2KV v2

    The same password, now stored, access-controlled and audited in Vault.

  3. Stage 3Dynamic

    No shared password: Vault creates a database user that expires in 30 seconds.

  4. Stage 4 · optionalKubernetes

    No Vault token either: the pod proves who it is with its service account.

  5. Stage 5 · optionalOperator

    No Vault code at all: the operator keeps a Secret fresh for a stage 1 app.

Stage 1 · no vault

The password lives in the app

The orders API gets DB_USER and DB_PASSWORD from its environment. It works, and that's the problem: the same password is in compose files, CI variables, and every copy of the container's config.

Send a request

What anyone with access to the host gets

This demo-only endpoint returns what the app holds. With a hardcoded password the same thing is visible through docker inspect, /proc/<pid>/environ, image layers or CI logs.

Look inside the app

One password, shared by every instance, valid until someone changes it, and no record of who used it.

Next. Move the password into Vault

Stage 2 · kv v2

The password lives in Vault

The app no longer has the password in its config. It authenticates to Vault with its own token and reads secret/app/db. Its policy allows exactly that one path, and the audit log records every read.

Send a request

How old is this password?

KV v2 keeps versions and timestamps. In this demo the secret is seeded at start-up, but in real life created_time is often years ago.

Secret metadata

Better: one place to store it, a policy for who can read it, and an audit trail. Still the same password, shared by every instance and valid until someone rotates it by hand.

Next. Stop sharing a password at all

Stage 3 · dynamic

Vault creates the credential, per request

The app asks the database secrets engine for credentials. Vault creates a new Postgres user with a 30-second lease, returns it, and drops the user when the lease ends. There is no shared password left to leak.

Send a request (click twice and compare db_user)

The lease behind the credential

Every dynamic credential has a lease. Vault tracks it, can revoke it early, and revokes it automatically at expiry.

Create a credential and look up its lease

Each request gets its own user. A credential is useless 30 seconds after it was issued, and the audit log ties every user back to the app that asked for it.

Next. Remove the last secret: the Vault token

Stage 4 · kubernetes auth

No token in the config either

Stages 2 and 3 still had one secret in the app's config: its Vault token (VAULT_TOKEN=app-dynamic-token), the "secret zero". Here the same orders API runs as a pod in a k3s cluster with neither a password nor a Vault token. It presents the service account token Kubernetes mounted into the pod; Vault asks Kubernetes whether that token is valid (TokenReview) and maps orders/orders-api to the app-dynamic policy.

Send a request to the pod

Nothing secret in the pod spec

Read the pod from the Kubernetes API: the environment has a Vault address and a role name, nothing else. The only credential is the token Kubernetes mounts at /var/run/secrets/kubernetes.io/serviceaccount.

kubectl get pod

The identity it presents, and what Vault accepts

The token names the namespace, the service account and even the pod it was issued to. The Vault role accepts only orders/orders-api with the cluster's audience.

Token claims and the Vault role

Same image, different service account

The reporting pod runs the identical image with identical settings, including the orders-api role name. Only its service account differs, and that is all Vault looks at.

Request from the reporting pod

This pod still contains Vault login code, and it uses the default service account token, which k3s issues for a year. The next stage removes both: the operator logs in for the app with fresh 10-minute tokens.

Next. Take Vault out of the app entirely

Stage 5 · vault secrets operator

The stage 1 app, with dynamic credentials

This pod runs the stage 1 configuration: it reads DB_USER and DB_PASSWORD from its environment and knows nothing about Vault. It has no Vault token and not even a Kubernetes service account token. The Vault Secrets Operator, installed into the cluster with Helm, logs in to Vault as orders/orders-vso, fetches dynamic credentials into a Kubernetes Secret, renews the lease, and restarts the app when it has to replace them.

Send a request (note source: env)

What the operator manages

One VaultDynamicSecret says what to fetch and what to restart. The operator owns the Secret it writes, and the app pod only references that Secret.

The resource, the Secret, the pod

Rotation, without the app noticing

Leases are 30 seconds, renewable up to 60. The operator renews at 67 % and, when the maximum is near, fetches new credentials and restarts the deployment. Expect a new database user and a new pod name after the wait.

Before and after 45 seconds

The app code is the same as in stage 1. Everything Vault-specific (login, lease renewal, rotation) lives in the operator, configured by three small Kubernetes resources.

The restart on rotation exists because environment variables are read once at start. An app that reads a mounted Secret file could pick up rotated values without one, after the kubelet's sync delay.

Policy · acl

Policies decide who can read what

Each app's token carries one policy. Vault denies everything else by default, and logs the denial.

Read a policy

Try a path as an app

A 403 here shows up in red in the audit log. The tokens use fixed ids to keep the demo simple; a real setup would use an auth method such as Kubernetes or AppRole.

Sentinel · enterprise

Policy as code: when, not just what

An ACL policy can only say which paths a token may use. A Sentinel endpoint governing policy adds conditions on top. Here: database credentials may only be issued inside a time window. Both have to pass: the app still needs its ACL policy, and now also the window.

Apply, try, remove

One of the two windows contains the current UTC hour (step 3 shows Vault's clock), so one allows and the other denies. The scenario removes the policy at the end so the other chapters keep working.

hard-mandatory: a denial is final. Asking for an override changes nothing.
soft-mandatory: a denial can be overridden with -policy-override, a break-glass that shows up in the audit log as override.

Next. Run it yourself

Run it

Run it yourself

The whole stack is ephemeral: Vault in dev mode, Postgres with no data volume, wiped on shutdown.

docker compose up --build -d                     # then open http://localhost:8080
export VAULT_ADDR=http://127.0.0.1:8200 VAULT_TOKEN=root
vault read database/creds/app                    # same as stage 3
vault kv get secret/app/db                       # same as stage 2
docker compose --profile k8s up --build -d       # adds stages 4-5: k3s, Kubernetes auth, the operator (~35 s)
docker compose down -v                           # removes everything
Demo-only shortcuts: Vault dev mode with root token root, fixed token ids, and /debug/creds + /probe endpoints on the app. Everything binds to 127.0.0.1. The Sentinel chapter needs Vault Enterprise.
